# Two bugs to file — synthesised chain shader

Both found by the width sweep in
[`bench_results/MODEL_SCALING.md`](../bench_results/MODEL_SCALING.md)
(2026-08-16, super-io / RTX 3060 Ti). Neither is in this repo's shader
catalogue — both are in the **synthesised** chain-shader path, whose GLSL is
generated by `Exmc.NUTS.CustomSynth.MultiRvCustomSpec` in the eXMC repos and
dispatched through this repo's `leapfrog_chain_synth*` NIFs. File against eXMC;
recorded here because the sweep that found them lives here.

---

## Bug 1 — `:nif_panicked` when observation count rises

**Severity: high.** A panic in a NIF takes down more than the caller.

Same IR, same generated shader, same `d`. Only `n_obs` changes:

| `n_obs` | result |
|---:|---|
| 60 | runs (3.2× slower than the CPU, but correct) |
| 600 | **`(Erlang error) :nif_panicked`** |

**Why it matters beyond the crash.** The trader's stated direction is *shorter
tick intervals and more data per sample* — i.e. increasing exactly this number.
A path that panics above 60 observations is not merely slow at the target
workload, it is unavailable there.

**Where to look.** The panic is on the Rust side, so it is a bounds or size
computation rather than a GLSL fault. Candidates, in order: the push-constant
`n_obs` field against the observation SSBO's actual length; the dispatch
geometry (`d` workgroups × 256 threads with a `q_shared[256]` tile, versus an
observation loop whose bound comes from `pc.n_obs`); and the descriptor set's
buffer sizing for the observation binding. Reproduce with
`bench_results/model_scaling/model_scaling.exs`, chain arm, `n_obs` 60 → 600.

**Done when.** Either it dispatches correctly at n_obs in the thousands, or it
returns `{:unsupported, _}` at synth time the way `push_too_large` already does
— a graceful refusal is acceptable, a panic is not.

## Bug 2 — the documented `d` cap is wrong by a factor of 20

**Severity: low, but it has already misled planning** (including a task brief
written from it this week).

The cap is documented and reasoned about as **d ≤ 256**. The real limit is the
128-byte f64 push-constants block, which measures out at:

| priors | max `d` |
|---:|---|
| general | **13** |
| `Normal` (two params each) | **6** |

`Exmc.Trading.RegimeModel` at d=8 fits with **one float to spare**. That is not
a comfortable margin for a model anyone intends to grow, and it means the
synthesis path cannot reach the widths where GPU compute starts to win against
an interpreter at all (~10³ elements) — let alone against EXLA.

**What to do.** Correct the figure wherever it appears, and treat it as a design
statement rather than a typo: a per-model push block caps model complexity at a
level below where the accelerator earns its keep. The alternatives are moving
prior parameters into an SSBO, or accepting that the chain-shader path is for
small models only and saying so in the same breath as the cap.

**Done when.** No document claims 256, and the real number appears next to the
`push_too_large` handling it explains.

## Context you will want if you pick these up cold

The chain shader exists to amortise ~30 dispatches per leapfrog step into one.
Measured at the width eXMC actually runs, it is **3.2× slower than
`BinaryBackend`**, and `BinaryBackend` is itself 20–215× slower than EXLA on the
same host's CPU. So neither bug is on a path that is currently winning. Fix them
because the code is shipped and a panic is a panic — not because fixing them
makes the chain shader the right answer. See the superseding banner on
[`bench_results/EXMC_PEROP_RACE.md`](../bench_results/EXMC_PEROP_RACE.md).
